작업: $ARGUMENTS
작업 파일: loops/$ARGUMENTS/  ·  기준 위치: 이 루트 저장소(허브)

이 명령은 **한 서비스가 아니라 루트 아래 서비스 전체(projects/*)**를 기준으로 계획한다.
features.json 은 **직접 편집하지 않는다.** 항목 추가는 `python3 scripts/loop.py add`, 수정은 `loop.py edit` 로만 한다
(다른 창이 레인을 진행 중일 수 있다 — 스크립트가 락을 걸고 id 중복·없는 선행·순환·잘못된 service 를 막는다).

0. `python3 scripts/loop.py status $ARGUMENTS` 를 먼저 본다. 모드는 셋 중 하나다:
   - **처음 계획** — 항목이 없다 → 1~5
   - **재정비** — `python3 scripts/loop.py lanes $ARGUMENTS --json` 의 `replan` 이 true (workloop 킷이 업데이트되어 규칙이 바뀜) → 6
   - **추가 계획** — 항목이 있고 replan 아님 → 1, 1-1, 2~5

1. loops/$ARGUMENTS/brief.md 를 읽는다. 없거나 양식 그대로(`(무엇을 만들거나 바꾸나)` 가 남음)면 "brief 먼저 작성" 안내 후 멈춘다.
   비어 있는 절은 모르는 것으로 본다. 추측으로 채우지 말고 필요하면 미결정 질문으로 올린다.
   brief 의 절이 design.md 로 이어지는 곳: 배경 → 한 줄 요약 · 누가 쓰나/대표 흐름 → 흐름도 · 범위 → 역할 표 ·
   비기능 요구 → 계약·check · 데이터/마이그레이션 · 배포/롤아웃 → 배포 순서와 롤백 · 의존/외부 · 열린 질문 → 리스크와 미결정.
1-1. **추가 계획** — 기존 항목의 id·done·notes·check·depends_on 은 그대로 둔다. 삭제·재번호 금지.
   - brief 에서 새로 생긴 요구만 design.md 끝에 `## 변경 YYYY-MM-DD` 절로 덧붙인다. 기존 절은 고치지 않는다.
     **항목을 하나라도 add 했으면 design.md 를 반드시 같이 쓴다** — `loop.py add` 가 계획 시각(planned_at)을 찍으므로,
     그 뒤로 design.md 가 안 바뀌면 대시보드가 "⚠ 계획보다 오래됨" 과 함께 `/work-plan` 을 다시 띄운다.
     같은 날 두 번째면 `## 변경 YYYY-MM-DD (2)` 로 이어 쓴다.
   - 새 항목은 다음 번호부터 (F09 까지 있으면 F10…).
   - 기존 **서비스 간 계약**(API 경로·필드명·테이블명)을 바꿔야 하면 바꾸지 말고 멈춰서 사용자에게 묻는다.

2. 관련 서비스를 정한다. brief 에 없으면 루트 README.md(서비스 현황이 있으면)와 projects/ 코드를 보고 판단한다. projects/ 가 없는 단일 저장소면 전부 "core" 레인이다.
   관련 서비스마다 projects/<서비스>/ 의 CLAUDE.md·agents/ 지침이 있으면 먼저 읽는다. 추측 금지 — 코드와 문서로 확인한 것만 쓴다.
   구조 파악이 크면 탐색 서브에이전트에 먼저 맡긴다. 코드는 수정하지 않는다.
3. loops/$ARGUMENTS/design.md 를 쓴다 (추가 계획이면 `## 변경` 절만). 섹션은 이 순서:
   - 한 줄 요약 (왜 하는가 포함)
   - 흐름도 (사용자 → 앱 → API → 내부 서비스 → DB, 이번 작업이 지나가는 경로만. 텍스트 화살표로)
   - 서비스별 역할 표 (서비스 / 바뀌는 것 / 안 바뀌는 것)
   - **서비스 간 계약**: API 경로·메서드·요청/응답 필드·에러 코드, 권한, DB 테이블·컬럼, env 이름, 캐시 키, 이벤트/큐 이름. 여기 적힌 이름이 모든 서비스의 기준이 된다.
   - 비기능 요구 (brief 에 있을 때): 성능 목표 · 보안/권한 · 개인정보 · 하위 호환 · 관측(로그·지표·알림)
   - 데이터·마이그레이션 (있을 때): 스키마 변경 · 백필 · 되돌릴 수 있는가
   - 순서와 병렬: 어떤 서비스가 먼저여야 하고, 무엇이 동시에 가능한지
   - 배포 순서와 롤백 (하위 호환 유지 방법·기능 플래그 포함)
   - 리스크와 미결정 사항 (brief 의 열린 질문 포함)
4. 항목을 JSON 파일로 쓰고 `python3 scripts/loop.py add $ARGUMENTS --file <파일>` 로 넣는다 (scratch 위치에 써도 된다).
   - 파일 형식: `{"goal": "한 줄", "services": [...], "features": [ {항목}, … ]}`
   - 항목 필드: id(F01~), service, desc, check, must_not(선택), owner("ai"|"human"), depends_on([id…]), notes(비우거나 한 줄 힌트). done 은 스크립트가 false 로 넣는다.
   - 스크립트가 거부하면 메시지대로 고쳐 다시 add 한다 (일부만 들어가지 않는다 — 전부 아니면 전무).
   - notes 는 비워 두거나 **한 줄 힌트**(예: `401 = 라우트 있음`)만. 근거·조사 결과·결정은 design.md 에 쓴다.
   - service: projects/ 아래 폴더명. 허브 저장소 자체 작업은 "core", 서비스를 넘는 통합 검증은 "e2e".
   - 계약을 **제공하는 쪽** 항목을 먼저, 쓰는 쪽은 그 항목을 depends_on 에 건다. 같은 서비스 안의 순서도 depends_on 으로 표현한다.
   - 서비스마다 레인이 독립적으로 돌 수 있게 나눈다. 불필요한 의존을 걸지 않는다. 한 레인은 한 창씩 순서대로 돈다.
   - 마지막에 e2e 항목으로 전체 경로를 검증한다 (예: 앱 요청 1건이 모든 서비스를 거쳐 기대 응답).
   - 항목 하나 = 30분 크기. check 는 실행 가능한 명령 + 기대 결과. 문장형 기준 금지.
   - **must_not = 경계 조건.** check 는 "됐는가", must_not 은 "하지 말았어야 할 것을 했는가" 다.
     실행 가능한 명령 하나이고 **0 이 아닌 종료코드가 통과**다 (0 이 나오면 경계를 넘은 것 → loop.py 가 done 을 거부한다).
     check 하나만 두면 그 지표에 맞추는 지름길이 열린다 — 테스트를 지우고, 값을 하드코딩하고, mock 을 남기고, 호출부를 주석 처리한다.
     **지름길이 있는 항목에는 반드시 붙인다.** 지름길이 없으면(파일 하나 추가 등) 비워 둔다. 억지로 만들지 않는다.

     | 항목이 이런 것일 때 | 열리는 지름길 | must_not 예 |
     | :--- | :--- | :--- |
     | 테스트를 통과시켜라 | 테스트를 지우거나 skip | `git diff --stat HEAD~1 -- '*_test.*' \| grep -q "deletion"` |
     | 응답에 값이 있어야 한다 | 값을 하드코딩 | `grep -rn "실제기대값" projects/x/src` |
     | mock 을 실제 연동으로 | mock 경로만 숨김 | `grep -rn "MOCK-REMOVE" projects/x/src` |
     | 에러를 없애라 | 에러를 삼킴 | `grep -rnE "except: *pass\|catch *\{ *\}" projects/x/src` |
     | 린트·타입 통과 | 무시 주석을 붙임 | `git diff HEAD~1 \| grep -q "^+.*\(nolint\|@ts-ignore\|eslint-disable\)"` |

     check 와 **같은 명령을 쓰지 않는다** (스크립트가 거부한다). 사람 항목(owner:"human")에는 붙이지 않는다.
     경계도 **몇 번을 다시 돌려도 안전**해야 하고 뒤 항목이 끝난 뒤에도 계속 통과(= 0 이 아님)해야 한다.
   - check 는 **항상 이 루트에서 실행된다** (대시보드·/work-next·/work-review 공통). 서비스 항목은 `cd projects/<서비스> && …` 로 시작한다.
   - check 는 **몇 번을 다시 돌려도 안전**해야 하고, **뒤 항목이 끝난 뒤에도 계속 통과**해야 한다 (review 가 나중에 다시 돌린다).
     "아직 없음"을 확인하는 check(예: 404 기대)는 쓰지 않는다.
   - 배포·마이그레이션 같은 비가역 동작은 check 에 넣지 말고 별도 항목(owner:"human" 또는 승인 필요)으로 빼고, check 는 그 결과만 확인한다 (예: `curl … | grep -q 401`).
   - 결제·콘솔·DNS·시크릿·prod 배포·번역 검수 등은 owner:"human".
5. **add 를 했으면 design.md 를 그 뒤에 쓴다** (순서: add → design.md). `ls -l loops/$ARGUMENTS/design.md loops/$ARGUMENTS/features.json`
   로 design.md 가 더 나중인지 확인한다. 아니면 대시보드가 설계 카드에 "⚠ 계획보다 오래됨" 과 함께 이 명령을 다시 띄운다.
   결과를 보여준다: ① design.md 요약 ② 서비스별 레인 표(서비스 / 항목 / 의존) ③ 처음에 병렬로 시작 가능한 레인 ④ 미결정 질문.

6. **재정비** (킷 업데이트 뒤 · replan:true) — 새 규칙에 맞게 **아직 안 끝난 항목만** 점검한다. 끝난 항목(done)은 건드리지 않는다.
   - 킷 업데이트 때 상태는 이미 옮겨졌다 (되돌아온 이력 → returns, 보강안 → check_fix, "실패" → 보류). 결과를 status 로 확인한다.
   - `status` 의 ⚠ 문제(없는 id · 순환 의존)를 먼저 고친다.
   - 미완료 AI 항목마다 4번 규칙에 비춰 본다: check 가 루트에서 도는가(`cd projects/<서비스> && …`) · 다시 돌려도 안전한가 ·
     뒤 항목이 끝나도 계속 통과하는가 · 문장형이 아닌가 · 비가역 동작이 섞였는가(→ owner:"human" 항목으로 분리) ·
     service 가 실제 폴더인가 · 불필요한 depends_on 이 레인을 막고 있지 않은가.
   - 고칠 것은 `python3 scripts/loop.py edit $ARGUMENTS <id> --check … | --desc … | --depends … | --owner … | --service … --why "재정비: 이유"` 로 고친다.
     진행 중(선점)인 항목은 스크립트가 거부한다 — 건너뛰고 보고한다. 새 항목이 필요하면 `add`.
   - 서비스 간 계약에 영향이 있거나 판단이 갈리는 변경은 고치지 말고 목록으로 사용자에게 묻는다.
   - 보류(hold)된 항목은 사유와 함께 보고만 한다 (unhold 는 사람이 한다).
   - 고친 것이 있으면 design.md 끝에 `## 변경 YYYY-MM-DD 재정비` 절로 **무엇을 왜 바꿨는지** 남긴다 (고친 게 없으면 쓰지 않는다).
   - 끝나면 `python3 scripts/loop.py replanned $ARGUMENTS` 로 재정비 표시를 지운다.
   - 결과: 고친 항목 표(id / 무엇을 / 이유) · 그대로 둔 항목 수 · 보류·질문 목록 · 지금 시작 가능한 레인.
